## Idempotency

The HTTP standard defines it like this: a request is idempotent "if the intended effect on the server of multiple identical requests ... is the same as the effect for a single such request" ([RFC 9110, §9.2.2](#sources)).

In plain words: **doing it twice has the same effect as doing it once.**

- **A lift button.** Press it five times and one lift comes. Idempotent.
- **"Add ₹40 to my bill".** Say it twice and you pay ₹80. Not idempotent.

A payment is naturally the second kind. Our job is to make it behave like the first.

### Why payments need it

The same request can reach the server more than once without anyone meaning to pay twice: a double tap, or a retry after the reply was lost. RFC 9110 explains that the point of idempotency is that a request "can be repeated automatically if a communication failure occurs before the client is able to read the server's response", knowing it "will have the same intended effect, even if the original request succeeded".

### How it works: idempotency keys

This is how Stripe documents it ([Stripe API docs](#sources)), and it's the pattern PocketPay will use:

1. "A client generates an idempotency key, which is a unique key that the server uses to recognize subsequent retries of the same request." Stripe suggests random V4 UUIDs.
2. The server saves the result of the first request with that key. "Retries with the same key return the saved response."
3. If a retry comes with the same key but different parameters, the server returns an error instead of guessing.

A new payment gets a new key, so a genuine second lunch is still charged.

## Money in flight

"In flight" isn't an official UPI term. It's common shorthand for **money that has left one account but hasn't been confirmed as arriving in the other.**

In NPCI's pay flow, the remitter bank debits you first, and the beneficiary bank credits the payee in a later step ([UPI primer diagram](/day-1/upi-primer#the-payment-step-by-step), steps 7 and 9). Between those steps the ₹40 has left your account but isn't yet in the canteen's. If the credit fails or no reply comes back, the money stays in that gap until it is reversed.

## Reversal

**A reversal puts money back with a new, opposite transaction. It doesn't delete the original.**

The rules:

- NPCI's guidelines say that when NPCI doesn't get a response in time, the transaction is treated as declined, and the reversal "will be generated by Beneficiary bank and/or NPCI as applicable" ([Guidelines](#sources)).
- RBI sets deadlines for UPI cases where your account was debited but the money didn't arrive ([RBI, 2019](#sources)):
  - **Paying a person:** auto-reversal "latest on T + 1 day".
  - **Paying a merchant** (like our canteen): auto-reversal "within T + 5 days".
  - In both cases, ₹100 per day compensation if it's later. "T is the day of transaction and refers to the calendar date."

**Example** (illustrative, not a real bank's format). Your statement shows both lines:

| Date | Description | Amount |
|---|---|---|
| 30 Oct | UPI payment to canteen@pocket | −₹40.00 |
| 31 Oct | Reversal of the payment above | +₹40.00 |
| | **Net effect** | **₹0.00** |

**PocketPay design:** our ledger works the same way. Postings are append-only, and mistakes are fixed with reversal entries, so the full history stays visible for support, audit and reconciliation.

## Reconciliation: why it's the company's problem too

**Reconciliation means comparing your own records with someone else's records of the same money, line by line, and fixing every difference.**

You might expect this to be only the banks' job, and banks do it. NPCI's guidelines say UPI members "must perform reconciliation", that "it will be the members' responsibility to verify accuracy of the Daily Settlement Reports with reference to the data available at their end", and that members "should have a separate operations and reconciliation team" ([Guidelines](#sources)).

But a payments company keeps records the banks can't see. Take a wallet company:

- **Each user's wallet balance.** RBI requires a non-bank wallet issuer to keep the money in an escrow account, and at the end of each day the escrow balance must not be lower than "the value of outstanding PPIs and payments due to merchants". The issuer must monitor this "on daily basis" and keep records of the daily position ([RBI PPI Master Direction, para 12.3](#sources)). The bank sees one escrow balance; only the company's ledger knows each user's share.
- **What the app told the user**, such as success or failed.
- **Rewards** given for each payment, and **refunds** in progress.

So banks check bank-to-bank, and **the company must check company-to-bank**, because only the company can check its own records. For a wallet company, RBI requires it.

### What a mismatch looks like

**Example** (PocketPay scenarios, not real data). Every night PocketPay compares its ledger with the partner bank's statement:

| Our ledger says | Bank says | What went wrong | Who's hurt if we miss it |
|---|---|---|---|
| Failed | Success | We gave up waiting and guessed | The teen: charged, but shown "failed" |
| Success | Failed | We trusted a reply we shouldn't have | PocketPay: we gave the merchant ₹40 and rewards for money that never came in |
| Credited twice | Credited once | We processed a duplicate confirmation twice | PocketPay: the wallet shows money that doesn't exist |
| Debited | Debited, then reversed days later | We missed the reversal | Both: our records and the user's balance are wrong |

## Check yourself

<details>
<summary>In one sentence, what is idempotency?</summary>

Multiple identical requests have the same intended effect as a single one (RFC 9110). For payments, the same request sent twice charges only once.
</details>

<details>
<summary>Who creates the idempotency key, and what does the server do with a repeat?</summary>

The client creates it (Stripe suggests a random V4 UUID) and reuses it for every retry of that request. The server saves the first result and returns it for any retry with the same key. A new payment gets a new key.
</details>

<details>
<summary>The canteen didn't get paid but your account was debited. How long can the reversal take?</summary>

Under RBI's 2019 rules, for a payment to a merchant: auto-reversal within T+5 days, with ₹100 per day compensation after that. For a transfer to a person it's T+1.
</details>

<details>
<summary>Banks already reconcile. Why does a wallet company need to as well?</summary>

Only the company knows each user's wallet balance, what status it showed, and what rewards it gave. RBI requires a non-bank wallet issuer's escrow balance to cover all outstanding wallet balances and merchant dues at the end of every day, monitored daily. NPCI also requires UPI members to reconcile against its settlement reports.
</details>
